## 1. The question and its scope (q1; D-100)

**Question:** *What does an AI accelerator's memory depend on, and who is known to make it?*

| Covered | How |
|---|---|
| Two products: NVIDIA H100 and AWS Trainium2 | the sources of the structural edges into HBM, found by the walk (§2) |
| One component class: High Bandwidth Memory | the target of both `incorporates` edges |
| One technology class: 3D die stacking | the target of HBM's `requires` edge |
| The actors on the chain | the activity edges into the chain's records (`navigate.py actors`): Amazon `designs` Trainium2 |
| Who makes each product's HBM | each `incorporates` edge's `supplier`: `not_researched` for both (D-094) |
| The recorded gaps | TSMC → H100 (D-092), drawn as a gap; three more §1 rows as text (§5) |
| Recorded nearby, not linked to either accelerator | SK hynix `operates` M16, and Micron's HBM4 36GB 12H (an instance of HBM), in a separate lane (the human's rulings below) |

**Not covered:** other accelerators; market shares, counts, rankings, "critical",
"concentrated" or any score (NG-11; S14–S15); policy; any fact the records do not hold. If the
journey needs one, the page shows a gap (Part B §16).

## 2. The derivation (q2; D-101)

The chain is **walked, never stored** (RR-5):

1. `navigate.Atlas.depends_on_tree("technology-3d-die-stacking")` returns the structural edges
   into 3D die stacking, then into each dependent: HBM `requires` 3D die stacking; H100 and
   Trainium2 `incorporates` HBM. The walk root is the journey's only hand-chosen chain ID: the
   deepest dependency the question reaches.
2. For each record on the chain, `Atlas.actors_list(id)` gives the activity edges into it.
3. For the component, `Atlas.supplier_rows(id)` gives each `incorporates` edge's `supplier`.
4. For every mark, `trace.trace_data(id)` gives the record, the claims it cites, their inputs
   (recursively) and their sources: the trace of `claim-model.md` §12, as data.

`tools/navigate.py --json` and `tools/trace.py --json` print the same structures (H-4). The
text outputs are rendered from them and are unchanged.

**Canonical only.** The build reads canonical records (`Atlas(data, include_staging=False)`), and
fails if a trace reaches a staging claim.

**What the build adds by hand** (the journey specification in `tools/build_page.py`): the walk
root; the lane's edge (SK hynix `operates` M16, named by H-1); the drawn gap's §1 row
(TSMC → H100, named by the prompt); the four §1 rows shown as text (§5); the decisions cited as
limitations. Each is an ID or a row key, never a value. The lane's products are not chosen: they
are the products whose `instance_of` includes the chain's component.

**The build refuses** (raises, so CI fails) when: the walk is empty; a lane record is linked to
either accelerator by an edge or a `supplier` assertion (the lane's text would then be false); a
§1 row or a decision is missing; a trace has a missing reference.

## 3. The visual form (q3; D-103)

**Form: a vertical dependency diagram**, drawn in inline SVG, read top to bottom. Every arrow
follows the taxonomy's direction convention: an actor points to what it acts on; a dependent
points to what it depends on. So "downwards" always reads "depends on" or "acts on".

**Why not a table or a network layout.**

- **A table** lists edges but hides the chain: the question is a path (product → part → process),
  and a path is read faster as a line than as rows. The text equivalent (§7) is the table, kept.
- **A force-directed network** places nodes by an algorithm, so position carries no meaning and
  changes when the data does. Here position encodes level in the chain, and a fixed layout lets
  the rebuild be byte-identical.

**Layout** (a 360-unit-wide `viewBox`, legible at 375 px without scaling below 0.9):

| Row | Contents |
|---|---|
| 1 — actors | Amazon (→ Trainium2, `designs`); TSMC (┄ H100, the recorded gap) |
| 2 — products | AWS Trainium2; NVIDIA H100 |
| 3 — component class | High Bandwidth Memory, with one supplier gap marker on each `incorporates` arrow |
| 4 — technology class | 3D die stacking |
| lane | a dashed-outline area: "Also recorded in the Atlas — not linked to any accelerator on this chain": SK hynix → M16 (`operates`), and Micron HBM4 36GB 12H ("recorded as a kind of" HBM: a property of its record, not a supply link) |

**Encoding** (each channel encodes one thing):

| Mark | Encodes | Drawn as |
|---|---|---|
| Node box | a canonical record | rounded box; type word and name from the record |
| Box fill and top rule | level: a named thing (company, product, facility) vs a vendor-neutral class (component, technology) | instance: white, thin border; class: tinted, thick top rule and the word "class" |
| Arrow | an edge, one relation type | arrowhead at the target; the relation type, verbatim, as its label |
| Solid line | stated: at least one cited claim is a `FACT` | solid |
| Dashed line + "inferred" | inferred: every cited claim is a `DERIVATION` | dashed, labelled "inferred"; the evidence panel shows the reasoning |
| Gap marker | an unknown value or a recorded gap | amber pill with a dashed border and the state in words ("not researched") or "gap: no edge"; a gap line is dotted, with no arrowhead |
| Lane | recorded, but not linked to either accelerator | a dashed-outline area with its own heading; no line crosses into the chain |

**What the visual does not encode:** magnitudes (no length, area or colour scales with a value;
the capacities stay text in their claims), confidence (no number exists, Part B §11), time (no edge
has a period; each shows "no period in the claims").

**Colour.** One ink for lines and text, one tint for classes, one amber for gaps. Colour is
never the only carrier: "inferred" and "gap" are written, and the line styles differ.

## 4. The editorial composition (q4)

In MA §19's order, as sections of one page:

1. **Headline:** the question, and a "Jump to" bar of the sections (D-108).
2. **Short answer:** one sentence composed from the records (the products, the part they share,
   what it requires, who makes it; omitted when the products do not share one relation type and
   one supplier state), then one line per edge on the chain and per supplier state, each with its
   basis (stated / inferred). No framing sentence depends on the data.
3. **Why it matters:** framing (it states no fact and names no record).
4. **The visual**, its legend, and "The chain in words" (the text equivalent).
5. **Key context:** what each product's maker states about its memory (the `incorporates`
   claims' statements), and the definitions of the two classes (their records' `definition`
   values). The capacities are quoted, never compared: they use different units and models.
6. **What the Atlas does not know** (§5).
7. **Evidence:** one panel per mark (§6).
8. **Method and limitations:** how the page is built, the input digest, the date range of the
   claims' verification and the sources' access, the rulings cited, and reproduction commands.
9. **Terms:** the schema definitions of every vocabulary value on the page.

**The text provenance rule** (D-105). Every text node on the page sits inside exactly one kind
of element:

| Kind | Attribute | Check |
|---|---|---|
| Record value | `data-ref` (an ID, a `schema:` or `doc:` reference) and `data-field` (a JSON pointer, or a table column) | the text equals the value at its home (a declared format may replace `_` by a space) |
| Absent value | `data-ref`, `data-field` and `data-absent` | the field is absent from the record; the text is a label |
| Label | `data-label` | the text is one of the build's fixed labels, none of which names a record or holds a digit |
| Derived | `data-derived` | the test recomputes it (the input digest, the date ranges) |
| Framing | `data-framing` | visibly marked "Atlas framing"; names no record (no name or alias of any record appears in it) |

Punctuation and arrows between annotated elements are allowed bare. A sentence such as
*TSMC makes the H100* cannot appear: "TSMC" would need a `data-ref`, and "makes" is no label.

## 5. Gaps (q5; D-104)

| Gap | Drawn | Text |
|---|---|---|
| HBM maker of each product: `not_researched` | an amber pill on each `incorporates` arrow, "supplier (who makes it): not researched" | the state's schema definition, and D-094's title |
| TSMC → H100 `fabricates`: a recorded gap (D-092) | TSMC's box, joined to H100 by a dotted amber line with no arrowhead and the pill "gap: no edge"; the legend and the lists say "a claim the Atlas holds, not an edge" (D-108) | the canonical `DERIVATION` `claim-tsmc-fabricates-h100` in its own panel, labelled inferred, with D-092's title |
| No recorded relationship (RR-7) | — | for each product with no activity edge, "no recorded relationship"; for the lane, "not linked to any accelerator on this chain" (recomputed by the check) |
| Rule codes in the quoted reasons | — | "Rules cited above": each ER-, RR-, F- or D- code with its one-line home (D-108). A section mark (§) gets one framing sentence pointing to the design record, not a guessed definition |
| Candidates that are not edges | — | four `edge-dataset.md` §1 rows: TSMC → H100 (with the drawn gap, above), and in a table SK hynix, Micron → NVIDIA; NVIDIA → H100; Micron → HBM4 36GB 12H. Their candidate, type and "why not" cells, attributed to the design record. The "sentence" cell is not shown: where it is not a claim, it is not canonical evidence |

**Never "none", never zero, never absence.** A gap has a mark and a word. The page never prints
"none"; the check fails on it.

**Why these four rows.** They are the rows that answer "who makes it?" for the records on the
page: the H100's fabricator and designer, the memory makers named at company level, and the HBM
product's fabricator. The other eight rows concern records off the page.

## 6. Evidence on the page (q6)

**Every mark is a link** (`<a href="#ev-ID">`) to its evidence panel. A panel renders
`trace.trace_data(ID)`:

- the record: its ID, type, name, and for an edge the sentence `<source> <type> <target>`, its
  level, its period ("no period in the claims" when it has none) and its `supplier`;
- each claim it cites, under the JSON path that cites it: type, status and statement first, then
  `as_of`, the citations, the reasoning, and last the claim ID, `verified_on` and review state
  (D-108). The claims of `legal_name`, `incorporated_in`, `headquartered_in`, `located_in` and
  `locality` sit in a closed disclosure: they say what a record is legally or where it is, which
  the question does not ask;
- each citation: the anchor (quoted) first, then source title, publisher, locator, class,
  standing, each stated date, access time, URL and the Verifier's read;
- for a `DERIVATION` (or `INTERPRETATION`): the reasoning, shown open, and its input claims in a
  disclosure ("Inputs to this inference"), recursively.

The reasoning of a `DERIVATION` is one click from its mark (Part B §02).

**Build stamp** (the human's ruling, D-102): a SHA-256 over the build's input files, listed by
path, in a fixed order. The page cannot carry the commit that contains it; the report records the
commit. `python tools/build_page.py --check` rebuilds and compares bytes.

**Dates.** Each claim's `verified_on`; each source's stated dates (or "undated") and access time;
each edge's period or its absence; and, in the method section, the range of `verified_on` and
of access times over the claims and sources on the page (derived, recomputed by the check).

## 7. Accessibility and mobile (q7)

- **Text equivalent:** "The chain in words", an ordered list generated from the same edges, each
  item linked to the same panel. The SVG has a `<title>` and a `<desc>`, and
  `aria-describedby` points to the list.
- **Keyboard:** every mark is an `<a href>`, focusable in document order, with a visible focus
  ring. Panels are always open; only derivation inputs sit in a `<details>`, whose `<summary>` is
  focusable.
- **Nothing only on hover:** there is no tooltip and no JavaScript. Every `:hover` rule shares its
  selector list with `:focus-visible`.
- **375 px:** a single column; the SVG is drawn for a narrow width; long IDs and URLs wrap.
- **Contrast:** every text colour against every surface ≥ 4.5:1, every mark colour against every
  surface ≥ 3:1 (WCAG 2.1 AA, 1.4.3 and 1.4.11), checked statically on the palette, and measured
  in the browser on the rendered text.
- **Structure:** `lang="en"`, one `h1`, no skipped heading levels, a skip link to the evidence.

## 8. Checks (q8; D-105, D-106)

**`validate-design` for this page** is `tests/test_page.py`, run in CI with every test module:

| Check | Fault it catches |
|---|---|
| PG-1 | a text node with no record, label, derivation or framing behind it |
| PG-2 | a `data-ref` value that differs from its home (a hand-edited label, a changed statement not rebuilt, a changed anchor or date) |
| PG-3 | a mark whose `data-ref` is not a canonical record, edge or claim (including a staging record), or whose link has no panel |
| PG-4 | an edge drawn as stated when no cited claim is a `FACT`, or as inferred when one is; an inferred edge without the word "inferred" or without its reasoning in the panel |
| PG-5 | a gap missing, drawn without its state, or as a zero; the word "none" |
| PG-6 | a framing block that names a record, or is not visibly marked |
| PG-7 | a rebuild that differs from the committed page, or two builds that differ |
| PG-8 | accessibility basics: `lang`, title, one `h1`, heading order, SVG title and description, a focusable link per mark, no `tabindex="-1"` on a mark, hover rules without focus, colours outside the palette, palette contrast |
| PG-9 | a link to a file that does not exist, or a fragment with no target; any `http(s)` resource loaded by the page (scripts, styles, images, fonts) |
| PG-10 | the build specification out of step with its homes: a §1 row, a decision or a lane record that no longer exists; a rule code quoted with no definition on the page |

**Browser QA (H-3):** a scratch Playwright run with the pre-installed Chromium, outside the
repository: desktop (1280 px) and 375 px screenshots; no horizontal scroll at 375 px; the Tab
path through every mark; Enter on a mark lands on its panel; the console and network logs empty;
contrast measured on every rendered text node. Results and screenshots go in the report.

**What the checks cannot see:** whether the framing reads well, whether a new user understands
the encoding, whether the order of sections suits the question. The human's new-user test (§9)
and the visual QA questions are the guard.

## 9. The new-user test (q9)

The human opens the page with no other document and:

1. answers the question from the page alone: what does each accelerator's memory depend on, and
   who makes it;
2. follows one mark to its source sentence, then to the source;
3. tries to break the chain: looks for a line that claims more than its evidence, a gap read as
   "none", an inference shown as fact;
4. notes every term that was unclear.

The findings go verbatim into `SESSION-11-REPORT.md`. Blocking ones are fixed in S11, or listed for
S12.

## 10. Candidates considered and rejected

| Candidate | Why not |
|---|---|
| A charting or graph library (D3, a graph layout) | NG-07; a fixed, hand-specified layout is clearer for four levels and makes the rebuild byte-identical |
| A page that reads the JSON at run time | H-2's alternative: needs JavaScript and a server or file access; the page could show values no check has seen |
| JavaScript for disclosure or highlighting | not needed: anchors and `:target` give the same path, and no script means no console errors |
| Drawing M16 or SK hynix next to HBM | no record links them; position would imply supply (the human's ruling) |
| A data commit on the page | a committed page cannot carry its own commit; CI's shallow clone sees one commit (the human's ruling) |
| Showing the §1 "sentence" cells | the memory-supplier sentence is not a canonical claim |
| A reusable component or design system | MA §16.1: two or three compositions first |
| Dark mode | doubles the palette to check; not needed for the slice |
