S14.5 — Visual Intelligence & Research UX Architecture
Type: RESEARCH / ARCHITECTURE / LIMITED IMPLEMENTATION
Mission
Establish the visual and interaction architecture for AI-Infrastructure-Atlas by studying high-quality data-intensive research products and translating their underlying UX and graphic principles into an Atlas-specific system.
The objective is not to redesign the entire website or imitate another product.
The objective is to define how:
`validated evidence → analytical derivation → insight → visualisation → exploration → evidence`
should operate as a coherent research experience.
Required benchmark set
Study and compare:

* Epoch AI
* Our World in Data
* International Energy Agency
* Stanford AI Index
* Datawrapper and/or another high-quality data-visualisation reference

For each benchmark assess:

* information architecture;
* navigation;
* content hierarchy;
* research-card patterns;
* chart interaction;
* filtering and exploration;
* editorial composition;
* typography;
* colour semantics;
* data density;
* responsive behaviour;
* accessibility;
* source and methodology presentation;
* relationship between insight, visualisation and underlying data.

For every major pattern classify it as:
`ADOPT | ADAPT | REJECT`
Do not copy branding, assets or layouts.
Atlas-specific objective
Translate the benchmark findings into a proposed Atlas UX model:
`QUESTION → INSIGHT → VISUAL → EXPLORE → EVIDENCE → DATA → METHOD`
The model must remain compatible with:

* canonical JSON as source of truth;
* DuckDB/SQL analytical layer;
* generated presentation;
* claim-level provenance;
* stated / inferred / gap semantics;
* deterministic derivations;
* existing vanilla HTML/CSS/JS architecture.

Required architectural outputs
Produce:

1. Visual design principles.
2. Minimal visual design system.
3. Analytical UX principles.
4. Proposed information architecture for the future Atlas site.
5. Component inventory.
6. Visual grammar for:
   * rankings;
   * timelines;
   * maps;
   * dependency diagrams;
   * KPI blocks;
   * comparison views;
   * evidence indicators;
   * analytical tables.
7. Evidence-aware visual semantics.
8. Rules for when a visual is appropriate and when a table/textual presentation is preferable.
9. Relationship between SQL outputs and visual components.
10. Clear boundary between S14.5, S15–S16 and S20.

Limited implementation
Create one controlled visual prototype using existing Atlas data.
The prototype should demonstrate the proposed visual language without replacing the current product architecture.
Prefer the existing HBM dependency slice as the test case.
The prototype should demonstrate, where supported by current data:

* editorial headline;
* analytical takeaway;
* KPI/indicator treatment;
* dependency visualisation;
* stated/inferred/gap visual semantics;
* evidence entry points;
* underlying analytical table.

Do not introduce a frontend framework.
Do not create a general-purpose dashboard system.
Do not create large amounts of new data solely for visual purposes.
Critical constraints
The session must not:

* modify `Eu-Digital-Policy`;
* introduce a runtime dependency on external APIs;
* replace canonical JSON with the SQL layer;
* create an opaque dependency score;
* redesign the entire repository;
* anticipate S20's full researcher-product implementation;
* compromise provenance for visual simplicity.

Validation
Evaluate the resulting prototype against:
Truth
Does the visual faithfully encode the underlying data?
Clarity
Can the intended relationship or comparison be understood quickly?
Context
Are scope, date, uncertainty, evidence status and relevant caveats sufficiently visible?
Presentation
Is the composition coherent, readable, responsive and accessible?
Architecture
Can the visual be regenerated from structured data rather than manually maintained presentation data?
Required session report
Document:

* benchmark findings;
* adopted/adapted/rejected patterns;
* visual principles;
* UX architecture;
* component decisions;
* prototype decisions;
* implementation constraints;
* deviations from the existing architecture;
* unresolved questions;
* implications for S15;
* implications for S20;
* technical debt introduced or explicitly avoided;
* verification results;
* exact files changed.

Acceptance criterion
S14.5 is complete only when the repository has a defensible answer to:
“What should an Atlas analytical research experience look and behave like, and how does that experience remain directly traceable to the evidence and analytical layer?”
The output must be sufficient for S15 to design dependency metrics with their eventual analytical presentation already understood, while leaving full researcher-facing product development to S20.
